Product Requirements Document: Online Clothing Store
Overview and Architecture
This web app is a serverless e-commerce platform (no custom backend) powered by Google Firebase and Paystack for payments. Firebase will handle all data storage, user authentication, file storage, and serverless logic 1 2 . For example, Cloud Firestore (NoSQL) will store product, category, order, and user data 1 , Firebase Authentication will manage user accounts with email/password sign-up 3 , and Firebase Hosting will serve the app’s front-end globally 4 . Cloud Functions provide “backend” capabilities without managing servers 2 – they will securely initialize and verify Paystack transactions and update the database via webhooks 5 6 . Firebase Storage will hold product images and any digital downloads 7 . All user interactions (product browsing, cart, checkout) run in the frontend and sync in real-time with Firebase, ensuring no dedicated backend server is needed.
Paystack integration uses its secure JavaScript “Popup” library to handle payments 8 . Transactions are initialized via a Firebase Cloud Function (storing the secret key securely) and completed in the browser using PaystackPop 9 10 . Upon payment completion, a Paystack webhook will trigger another Cloud Function to verify and record the order in Firestore 11 12 . This approach aligns with Paystack’s guidelines: “Never call the Paystack API directly from your frontend” – all sensitive calls happen in secured server-side functions 5 .
User Roles and Authentication
There are two main roles: Customers and Admin (with a super-admin). Users can register/login with email and password via Firebase Authentication 3 . No social login or phone is required per spec. Each user’s account will store billing/shipping details and order history. The Admin Dashboard is a separate, password-protected web interface. A super-admin login controls access. Admins manage products, categories, filters, and inventory. Since there’s no custom server, Admin functions also use Firebase (Firestore and Cloud Functions) under the hood, protected by Firebase security rules and a separate admin UID check 5 .
Catalog Structure
Products are organized into categories and subcategories: - Men’s Category: subcategories “Clothing”, “Jersey”, “Accessories”. - Women’s Category: subcategories “Top”, “Bottom”, “Swimwear”, “Accessories”, “Jersey”. - Other Categories: “Sale”, “New Arrivals”, and “Collections”.
The admin sets these categories and assigns each product accordingly. Users browse by category. When a category is selected, the app displays a Product Listing showing all items in that segment. The site must allow filtering the list by multiple attributes: e.g., product type (subcategories), available sizes, availability (in-stock only), color, and price range. Filters are critical for usability – e-commerce UX research shows that providing filters like price, color, and size are “essential” for helping users narrow down products 13 . The UI should allow selecting multiple filter values (e.g. women’s tops that are red

Product Details and Filters
Clicking a product in a listing opens the Product Page, which displays comprehensive details. The page shows multiple images (front, back, side views) of the item; users can click or swipe through them. It lists available sizes (e.g. S, M, L), available colors, price, and stock status (e.g. “In Stock” or “Out of Stock”). The admin provides a detailed description, plus any features or specifications (material, care instructions, etc.). The page UI lets the user select color, size, and quantity. There are buttons to “Add to Cart” or “Add to Wishlist”.
The available filters (product type, size, availability, color, price) are derived from product attributes stored in Firebase. When the admin adds or updates a product in the database, they specify all applicable filter attributes. The frontend automatically reads those fields from Firestore to populate the filter UI. For instance, if the admin tags a new shirt as color “Blue” and size “M”, those options appear under the color and size filters on the relevant category page.
Shopping Cart and Checkout
Products added to the cart are stored in the user’s session and in Firestore (so cart data syncs across devices). The Cart Page lists all chosen items with image, name, selected size/color, quantity, and subtotal. Users can update quantities or remove items. The page shows the total price.

User Account and Order History
The Account Page allows users to manage their personal information and orders. Sections include: - Orders: A list of past orders with status (paid, shipped, delivered). Users can click to see details of each order. - Account Details: Name, email, password change option. - Wishlist: Items the user saved for later. - Downloads: If digital products are offered, download links for those fulfilled purchases. - Billing Details: Stored addresses; user can add/edit addresses. - Payment Methods: (Optional) stored card references (if implementing Paystack card on file). - Logout: Securely sign out of Firebase Auth session.
All user data (orders, wishlist, etc.) is fetched from Firestore. The UI should allow the user to update their billing address, which is then used as default on future checkouts.

Admin Dashboard
The admin interface is a protected web dashboard (built as a separate part of the app). It requires admin login (Firebase Auth can restrict to specific admin emails/UIDs). The dashboard supports:
• Product Management: Add/Edit/Delete products. For each product, the admin enters name, category/subcategory, detailed description, feature list, price, available sizes, colors, and availability status. Multiple images can be uploaded (each product supports multiple views) – these are stored in Firebase Storage with links saved to Firestore. The admin can set “inventory count” to track stock. If inventory is enabled, selling a product decrements its stock in Firestore; products go out of stock when count reaches zero.
•Category & Filter Setup: Define the top-level categories (Men, Women, Sale, etc.) and subcategories. Also define filter attributes (like additional product types or tags). These define how products are grouped and what filters appear on the frontend.
• Inventory Management: The admin dashboard provides an overview of product inventory. It shows current stock levels and can alert when items are low in stock. The admin can update stock counts manually if needed. (Since Firestore updates in real-time, inventory data syncs instantly.) Managing inventory ensures accurate “Availability” status on product pages.
• Orders Admin: View all customer orders (status, details). Orders are listed from Firestore (populated via the checkout Cloud Function). The admin can mark orders as shipped or canceled.
• Settings: Manage other site settings (e.g. collections, sale rates).
All admin data (products, inventory, orders) live in Firebase. The dashboard UI calls Firebase directly (or through Cloud Functions for sensitive ops) to perform CRUD operations. For security, Firebase Security Rules restrict database writes to admin accounts for these collections.

Technical Considerations
• Serverless (No Backend): By using Firebase, the app remains “backendless”. Firebase’s services replace a traditional server. For example, Firebase Cloud Functions handle server-side tasks (payment processing, webhook handling) 5 6 . All client–server communication (product data, user actions) uses Firebase’s APIs (Firestore SDK, Auth, etc.).
• Database Schema: Firestore will have collections like products , orders , users , and categories . A product document includes fields for name, categoryId, price, description, imageURLs[], availableSizes, colors[], inStock (boolean or count), and any specs. Orders store
itemIDs, quantities, total price, userID, status, and timestamp.
• Inventory Management: Since inventory is required, each product has a stock count. Cloud Functions triggered on order completion will decrement stock and set inStock=false if zero. The admin can override these counts manually. Realtime Database or Firestore ensures inventory updates are reflected instantly across clients.
• User Experience: The site should be responsive and intuitive. Key UX best practices include: providing multiple product images (3+ thumbnails as recommended 17 ), clear filter UI, and showing applied filters at a glance 15 . The checkout flow should be smooth, using Paystack’s secure popup for convenience 8 .
• Security: Firebase handles authentication and database security. Sensitive operations (like initializing payments) occur in Cloud Functions (never exposing secret keys to the browser) 5 . Paystack webhooks also go to Firebase (HTTPS trigger) to securely record payment statuses 6 . All user inputs (login, product forms) go through client-side validation and Firebase’s rules.

• Digital Downloads: If the store offers digital products, the checkout will grant a downloadable file. After payment verification, Cloud Functions can attach download URLs (from Firebase Storage) to the user’s order or account for access on the Downloads tab.
In summary, this serverless e-commerce app will use Firebase for the entire backend functionality (data storage, auth, hosting, functions) 1 2 and Paystack for payments 8 18 . It will support all required features: user accounts, product browsing with category filters, product detail pages, cart/checkout, order management, inventory control, wishlist, and admin operations – with no custom server code beyond Firebase functions. The app architecture leverages modern cloud services to provide security, scalability, and real-time updates.
